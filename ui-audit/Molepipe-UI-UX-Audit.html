1 · Scope & method

The ui-audit/ folder documents a complete user journey captured over CDP-driven interaction and adb screencap: fresh install → account creation → friend request → two-way messaging (text + images) → lock/security states, in both portrait and a landscape pass that crosses the app's 900 px two-pane breakpoint, plus an image-send retest.

Revision 2 narrows the lens to two questions:

  • Material 3 design language & features — are the M3 colour roles, type roles, shape scale, elevation ladder, motion and state layers actually driving the UI, and which M3 features/components are used, hand-rolled, or vendored-and-ignored?
  • Consistency across surfaces — when the same job appears on different panels and tabs (a primary action, a cancel, a back, a selection, a selected state), does it look, read and behave the same way, all the way down to individual buttons and to how people navigate and select?

Findings were produced by cross-referencing three evidence streams:

  • Walkthrough claims — the state descriptions in ui-audit/README.md;
  • Pixel analysis — per-frame luminance/colour sampling, region diffs and MD5 de-duplication of the capture sets (which corrected several README captions, e.g. 54-image-delivered.png is byte-identical to the failed state, and the "actions bar" frames are duplicates);
  • Source audit — line-level review of the four UI files and the vendored Material Web bundle (a WebView shell serving one HTML/CSS/JS app with generated Material 3 colour tokens).

Severities: High functional breakage, severe UX failure, or accessibility blocker · Medium consistency/hierarchy defect visible in normal use · Low polish. Status: Fixed · Partial · Open (this consistency pass) · Backend. Findings carried over from Rev 1 keep their legacy ID as (was X-n).

2 · Executive summary

The app's Material 3 foundations are now genuinely strong: a complete 36-role colour system with seven accents plus runtime Material You palettes, a documented shape and type scale, correct M3 elevation recipes, and honest Tor/destructive-confirmation UX. The remaining risk is not the foundations — it is drift between surfaces. The same concept still resolves differently depending on where you stand:

  • Three switch mechanics for three tiers of navigation (bottom nav, wizard, You sub-tabs) with three different active-state and ARIA expressions;
  • Selected-state colouring is split — segmented toggles highlight on primary-container while tabs, theme buttons and nav highlight on secondary-container;
  • Button hierarchy varies per surface — the confirm dialog is the only dialog whose Cancel is a filled-tonal twin of its confirm; "Copy", "Scan QR" and "Cancel" each appear in two or three different button styles; Accept/Decline changes grammar per request type;
  • Navigation and selection affordances are close but not one system — back/close glyphs fork three ways; multi-select carries no ARIA at all while the You tabs carry a half-implemented one.

Underneath that drift, the Material 3 component layer is only half-adopted: buttons, text fields, switch, list and linear progress are real md-* elements, but dialogs, menus, the navigation bar, tabs and the FAB are hand-rolled against the M3 spec — while md-dialog, md-menu, md-tabs, md-ripple and md-focus-ring sit vendored and unused (§4, §12).

M3-12Half the Material Web bundle is vendored and unused; core chrome is hand-rolledMediumOpenComponents

The bundle registers the full Material Web set, but the app only consumes buttons, text fields, switch, list and linear progress. Everything that gives M3 its interaction language — dialogs, menus, tabs, icon buttons, FAB, ripple, focus ring — is hand-rolled to look right rather than behave right. That is the root cause of the selection/navigation gaps in §7–§8: the hand-rolled menu cannot get keyboard interaction for free, and the hand-rolled tab strip cannot get roving tabindex for free.

5 · Consistency · panels & tabs

Three tiers of "switchable surface" exist — bottom-nav tabs (Chats/Requests/You), wizard steps, and the You sub-tabs (Profile/Preferences/Devices/Security) — plus detail panes (add screen, group info, chat) and in-modal micro-wizards (duress). The look converges; the mechanics do not.

PT-1Three different switch mechanics for three tiers of navigationMediumOpenPanels · mechanics

Bottom nav, detail panes and wizard steps swap via the hidden attribute (setTab, showDetail, wizGoTo); You sub-panes swap via a .pane-on class on [data-you-pane] wrappers; the duress setup is a third micro-pattern (showDuressStep toggling hidden on 3 in-modal steps with its own Back buttons). Anyone changing "how panes appear" must know which mechanism each tier uses.

app.js:746–768 (setTab) · :701–725 (showDetail) · :770–779 (showYouPane) · :3116–3143 (wizGoTo) · :2623–2625 (showDuressStep) · style.css:1707–1708

Open gap: one showPane(el) primitive (hidden + focus + optional history) for all tiers; You panes currently need the class form only because sibling wrappers share a pane id — that can become a single container per pane.
PT-2Active state and ARIA expressed three ways; none is a complete tab patternMediumOpenPanels · ARIA

Bottom nav items: .active class only — no aria-current, no aria-selected (index.html:728–730). You tabs: aria-selected on role="tab" buttons inside role="tablist" — but no aria-controls anywhere in the app, no role="tabpanel" on the panes, no roving tabindex, no arrow-key handling. Wizard: no tab roles at all, but compensates with focus-to-heading + "Step N of M" aria-live. Three different announcements for "where am I".

app.js:762 (class-only) · :775 (aria-selected) · :3133–3142 (wizard focus) · index.html:408–413 (tablist without panels)

Open gap: decide the pattern per tier and finish it — M3 navigation bar semantics (aria-current="page") for .navitem; full ARIA tabs (controls + roving tabindex + ←/→) for .you-tabs; wizard already models a linear flow correctly.
PT-3Selected-state colour and shape split across tab-like controlsMediumOpenPanels · selection colour

All four "pick one" controls look like siblings but highlight differently: .seg (person/group, group policy, wipe threshold) uses primary-container on a shape-m track; .mode-btn (theme Auto/Light/Dark) uses secondary-container with no shared track at all (3 independent outlined pills); .you-tab uses secondary-container on a shape-full track; .navitem uses a secondary-container pill indicator. In M3 terms, primary-container means "selected" in segmented buttons and secondary-container in tabs — the app uses both for the same job with no rule.

style.css:1032–1043 (.seg) · :866–873 (.mode-btn) · :1683–1705 (.you-tab) · :727–735 (.navitem)

Open gap: write the rule down and follow it — recommended: segmented buttons = primary-container, tab strips / nav = secondary-container — then move .mode-btn into the .seg track pattern (it is a segmented control without a segment).

After the polish pass Chats is one tonal primary + two text secondaries and the FAB hides — but Requests still presents two md-filled-tonal peers ("Add someone", "Share my code") with no primary, and the detail/search empty states have no CTA at all.

8 · Consistency · selection

How people choose: long-press menus, multi-select, segmented toggles, swatches, pickers. This is the least consistent interaction family in the app — and the one where hand-rolled components (M3-12) cost the most.

SL-1Keyboard/switch users could not use menus or dialogsHighPartialSelection · accessibility(was A-1)

app.js:299–392, 2865–2878, 458–468 (pre-fix)

Resolved: shared Tab trap + focus-restore on the confirm/edit dialogs; wizard focuses each step heading and announces "Step X of 8" via aria-live; viewer focuses its close control.
Open gap: menus still have no keyboard interaction (see SL-3); this is what the deferred md-menu migration buys.
SL-2Multi-select carries no ARIA, and its state class collides with long-pressMediumOpenSelection · semantics

app.js:4980–5043 (selectMode) · :4662–4668 (long-press highlight) · style.css:1285–1301

Open gap: role="listbox"/aria-multiselectable on the message list during select mode (or aria-pressed per row), an accessible name on the select bar ("3 selected"), and distinct visuals for pressed vs checked.

9 · Flow-level findings (preserved from Rev 1)

Kept for traceability. These are journey-level defects rather than design-language ones; the design-language consequences of each are captured above.

FL-1Most consequential chat text was the smallest — and not a controlHighFixedHierarchy(was T-2)

"Not delivered — couldn't send · tap to retry" rendered at 0.7rem (~11px) with a ~15px hit target (⅓ of the 44px floor) while the failed image was a 260px dimmed square whose tap opened the full viewer.

style.css:872 · app.js:1704–1714, 3828

Resolution: failure cause moves to a label-size error line; Tap to retry is a ≥48px error-container pill with refresh icon; group chats gain the same states (previously none).
FL-2Wizard PIN step validated nothing; empty submit fired a raw server errorHighFixedUX practice(was O-3)

Label promised "6+ digits"; only equality was checked. But the deeper defect was that the step could not succeed for any user, ever: POST /api/security is s.auth()-gated on a vault session token, and no session exists anywhere in the wizard — setSessionToken() runs only in doUnlock(), reached from the "Start messaging" button two steps later. pinEnable needs the live unlocked identity (it reads MnemonicString()/PassphraseString()), so no pre-unlock session could ever have served it. Reproduced on a host instance: POST /api/create returns {account_number, recovery_phrase} with no session_token, and the pin-enable call answers 401 with the plain-text body unauthorized — not JSON, so body.error was undefined and the UI always fell back to its own generic string (walkthrough 13c: "Could not turn on PIN unlock.").

app.js:2957–2968 (pre-fix) · ui-audit/13c, L13c

Resolution: client validates /^\d{6,}$/ + match with inline field-adjacent errors; the step then holds the PIN (wizPendingPin) and makes no network call at all, and wiz-finish applies it immediately after doUnlock() mints the session — the first moment the endpoint can succeed. Deferring was chosen over minting a session at the PIN step: a live token mid-wizard makes refresh() take its sessionToken && unlocked branch and drop the user into the chat view on the next WebView rebuild, and it would start the onion service three steps earlier, moving publish timing for no user-visible gain. A genuine failure now surfaces as a snackbar naming You›Security rather than silently leaving the PIN off. No backend change was required — the earlier follow-up (widen POST /api/security to a "pre-unlock onboarding session") was misdirected: there is no onboarding session to widen to, and inventing one would move an auth boundary for one wizard step. Verified by driving the shipped wizard over CDP against a host instance: pre-fix the same script reproduces frame 13c exactly (stuck on step pin, banner visible, pin_enabled:false); post-fix the PIN step makes zero requests, advances to done, and GET /api/security reports pin_enabled:true. "Not now" still ends at pin_enabled:false.

10 · Strengths preserved

  • Complete M3 colour foundation — 36 system roles with a full surface ladder, seven accent schemes, and runtime Material You palettes bridged from Android; surfaces consistently draw from surface-container-* roles.
  • Honest Tor status system — four token-coloured states, a split "Send ✓ / Receive ⟳" pill that refuses to say Online before the descriptor publishes, determinate bootstrap bar, stall detection; the pill remains tappable into Diagnostics with an honest accessible name.
  • Lock-screen security UX — no fixed-length PIN placeholders, scramble-on-failure, explicit attempt countdown, forgot-PIN escape always one tap away, consequence-first destructive disclosure copy.
  • One confirmation architecture — every consequential action routes through confirmDialog with honest titles and consequence-named buttons.
  • Explicit hardware-back chain — one ordered handler (overlays → menus → viewer → dialogs → wizard → select mode → detail → tab → exit) with Esc delegating to it.
  • Text-safety discipline — user-controlled strings only ever reach textContent/createTextNode; the three innerHTML template sites are static-only and documented.
  • Long-press implementation — 500ms with cancel slop, click-swallow and haptic; the image viewer's pinch/double-tap separation is above average.
  • Numbered phrase grid — CSS-counter ordinals keep textContent as the bare 24 words, which is what lets secret-wiping work reliably.
  • Two-pane master-detail — divider at the 400px minimum, chat pane exempt from the form-width cap, bubbles capped at a readable min(82%, 620px) measure.
