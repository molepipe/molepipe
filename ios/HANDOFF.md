# iOS Port Handoff

This document covers everything needed to build and run Molepipe on iOS. The
iOS port follows the same architecture as Android: Go gomobile wraps the backend
into a framework, Rust torhost provides the Arti onion service, and a native
shell loads the shared web UI.

## macOS-Only Build Checklist

Everything below requires macOS with Xcode. Cannot be run from Linux.

### Prerequisites (one-time)

```bash
# Rust iOS targets
rustup target add aarch64-apple-ios aarch64-apple-ios-sim

# gomobile
go install golang.org/x/mobile/cmd/gomobile@latest
go install golang.org/x/mobile/cmd/gobind@latest
gomobile init

# xcodegen
brew install xcodegen
```

### Build Steps

```bash
cd ios

# Step 1: Cross-compile Rust torhost for iOS
# Produces: ../backend/internal/tor/artihost/lib/ios-arm64/libtorhost.a
#           ../backend/internal/tor/artihost/lib/iossim-arm64/libtorhost.a
bash build-torhost.sh

# Step 2: gomobile bind → XCFramework
# Produces: Mobile.xcframework  (module name MUST be "Mobile", not "Molepipe" —
# see Troubleshooting: the app target's own module is "Molepipe")
bash build-xcframework.sh

# Step 3: Generate Xcode project
# Produces: Molepipe.xcodeproj/
xcodegen generate

# Step 4a: Build for simulator (CLI)
bash build-app.sh --simulator

# Step 4b: Build for device
# Open Molepipe.xcodeproj in Xcode, set signing team, run from Xcode.
```

## Architecture Parity Notes

| Concept | Android | iOS |
|---|---|---|
| Backend wrapper | `Backend.kt` (singleton object) | `Backend.swift` (final class, `@Published`) |
| Service lifecycle | `BackendService` (foreground service) | `BackendService.swift` (background tasks) |
| WebView bridge | `@JavascriptInterface` inner class | `WKScriptMessageHandler` + JS injection |
| Save image | `MediaStore` + `ContentValues` | `PHPhotoLibrary.shared().performChanges()` |
| Share image | `Intent.ACTION_SEND` + `FileProvider` | `UIActivityViewController` |
| Open URL | `Intent.ACTION_VIEW` | `UIApplication.shared.open()` |
| Dynamic color | Material You `system_accent1_*` | Stub `""` (no equivalent) |
| Status bars | `WindowInsetsControllerCompat` | `UIStatusBarStyle` / `overrideUserInterfaceStyle` |
| Background | Foreground service + `PARTIAL_WAKE_LOCK` (runs indefinitely) | `beginBackgroundTask` grace window only, then suspended (see divergences) |
| Notifications | `NotificationManager` + channels | `UNUserNotificationCenter` |
| Tor dormant | `setDormant()` → `DormantMode::Soft` | Same Go call via gomobile |
| Back button | `handleAndroidBack` JS callback | `WKWebView.canGoBack()` |
| Kill = stop | `onDestroy` → `Backend.stop()` | `willTerminate` → `Backend.stop()` |
| Seed at rest | password-encrypted `identity.enc` in app-private storage (OS FBE) | password-encrypted `identity.enc` + Data Protection (`completeUntilFirstUserAuthentication`) + excluded from iCloud backup |
| Biometric unlock | (not implemented) | `Keychain.swift`, biometric-gated vault-password slot (Swift ready; web opt-in pending) |

Note the "Background" row is an API mapping, **not** a behavioural equivalence — see Platform divergences below.

## Regenerating the XCFramework

When Go core code changes (new/modified exported functions in `mobile/`):

```bash
cd ios && bash build-xcframework.sh
```

The Rust static libraries do NOT need to be rebuilt unless `torhost/` changes.

## Regenerating the Xcode Project

When adding/removing Swift files or changing build settings:

```bash
cd ios && xcodegen generate
```

The project.yml is the source of truth; the .xcodeproj is gitignored.

## Troubleshooting

### `cargo build` fails with "target not found"
Run: `rustup target add aarch64-apple-ios aarch64-apple-ios-sim`

### `gomobile bind` fails with "unable to find import"
Ensure the Rust static libraries exist in `backend/internal/tor/artihost/lib/ios-arm64/`
and `lib/iossim-arm64/`. Run `build-torhost.sh` first.

### `xcodegen generate` fails
Ensure xcodegen is installed: `brew install xcodegen`. Check `project.yml` for
YAML syntax errors.

### Xcode build fails with "no such module 'Mobile'"
The Swift shell does `import Mobile`, so the framework MUST be named
`Mobile.xcframework` (gomobile derives the module name from the `-o` basename in
`build-xcframework.sh`). Do NOT rename it to `Molepipe` — that is the app target's
own module name and the two would collide. If the module is missing entirely, the
XCFramework wasn't built: run `build-xcframework.sh` first.

### Link fails: "building for iOS Simulator, but linking in object file built for iOS" (or vice-versa)
Wrong torhost slice. The device/simulator `libtorhost.a` are chosen by SDK in
`project.yml` (`LIBRARY_SEARCH_PATHS[sdk=iphoneos*]` vs `[sdk=iphonesimulator*]`),
NOT by Go build tag — device and simulator are both `ios/arm64`. Check both paths
exist (`build-torhost.sh` writes `lib/ios-arm64/` and `lib/iossim-arm64/`) and that
`OTHER_LDFLAGS` still carries `-ltorhost`.

### Link fails: undefined symbols `_torhost_*`
The gomobile framework intentionally leaves the torhost symbols undefined; they are
resolved at app-link from `libtorhost.a`. Confirm `OTHER_LDFLAGS: -ltorhost` and the
per-SDK `LIBRARY_SEARCH_PATHS` in `project.yml`, and that `build-torhost.sh` ran.

### Build fails: "Mobile.framework is a static framework and cannot be embedded"
gomobile emits a STATIC xcframework, so `project.yml` links it (`embed: false`). This
error means it's set to embed — keep `embed: false`. (Conversely, if a gomobile
version emits a *dynamic* framework and the app crashes at launch with a dyld
"Library not loaded: @rpath/Mobile.framework" error, flip to `embed: true`.)

### Undefined symbols for the Go runtime (e.g. `_OBJC_CLASS_$_...`, Security/CFNetwork)
The static gomobile lib pulls in Apple system frameworks the Go runtime uses. If the
app link reports these, add them to `OTHER_LDFLAGS` (commonly
`-framework Security -framework CoreFoundation`). Left out by default to avoid
over-linking; add only what the linker actually names.

### "NotificationHandler does not conform to MobileMessageListener"
The reverse-bound protocol's exact selector labels and parameter nullability are
gomobile-version-dependent. Open the generated header inside `Mobile.xcframework`
(`.../Headers/Mobile.objc.h`), find `@protocol MobileMessageListener`, and match the
Swift method signatures in `NotificationHandler.swift` to it — Xcode's fix-it will
usually offer the exact form.

### WebView shows blank page
The backend URL may have expired. The app should automatically reload when
the backend state changes. Check console logs for backend start errors.

## Crypto Constants (DO NOT CHANGE)

These constants are part of the wire protocol and must not be modified:
- `"onion-chat/v1"`, `"onion-chat/v2"` — protocol identifiers
- `"onionchat-update-manifest-v1"` — update manifest signing
- `"onionchat-pair:"` — pairing prefix

## Platform divergences (iOS ≠ Android)

These are real behavioural differences, not polish. They come from the platform,
not the port, and cannot be closed by more Swift.

1. **Background execution — the big one.** Android's foreground service keeps the
   backend and the Tor onion service running while backgrounded, indefinitely.
   iOS has no equivalent: the app is suspended within seconds of backgrounding
   (`beginBackgroundTask` buys only a short grace window). **Consequence:** the
   onion service is reachable only while the app is foregrounded. A message sent
   while this device is suspended waits in the *sender's* mailbox/relay and syncs
   on next foreground — it does not arrive live, and no notification fires until
   then. There is no supported iOS mechanism to hold a long-lived onion service
   open in the background; the only real mitigation is a future APNs "wake" push
   (see below), and even that only gives a brief fetch window, not a live socket.

2. **Seed at rest — Keychain vs Keystore is a red herring.** Android does not use
   the Keystore for the seed; it keeps the password-encrypted `identity.enc` in
   app-private storage protected by OS file-based encryption. iOS matches that and
   adds two protections (see `BackendService.dataDir()`): Data Protection
   (`completeUntilFirstUserAuthentication`, files inherit the dir's class) and
   exclusion from iCloud/Finder backups. The seed is deliberately **not** moved
   into the Keychain: its root of truth is the recovery phrase and it must stay
   recoverable on any device, so binding it to this device's Keychain would break
   cross-device recovery. Both platforms depend on a device passcode/credential —
   with none set, neither can protect data at rest.

3. **Keychain, used for what it's for.** `Keychain.swift` holds only an *opt-in,
   biometric-gated copy of the vault password* ("unlock with Face ID"), device-only
   and never backed up. Losing it costs a password re-entry, never the account.
   The Swift + `ShellBridge` (`keychainSet`/`keychainGet`/`keychainDelete`) plumbing
   is in place and needs `NSFaceIDUsageDescription` (already in Info.plist); the web
   unlock screen still has to call it to offer the toggle (see Future Work).

4. **Apple-native share/save.** `UIActivityViewController` and `PHPhotoLibrary`
   replace Android's Intent/MediaStore. Behaviourally equivalent.
